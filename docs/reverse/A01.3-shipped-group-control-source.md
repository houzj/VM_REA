# A01.3 原厂 GroupControl 宿主顺序

安装版样例 `GroupControl\Form1.cs` 的 SHA-256 为 `BE74249C77E551F9568B69F2A89710F39A6982ABA8B63AD2AD09AEB2B078CD29`。源代码把独立 Group 的宿主边界明确分成四条操作链。

- 导入按钮调用 `IMVSGroupTool.LoadIndependentGroup(path)`。只有调用成功后才写入 `mGroupTool`，再把它赋给 `VmSingleModuleSetConfigControl.ModuleSource`。`VmException` 被捕获并以十六进制错误码写入消息列表。
- 导出按钮先要求路径非空和 `mGroupTool` 非空，然后调用 `mGroupTool.SaveAs(path)`，错误同样转换为十六进制错误码。
- 单次执行先通过名字 `mGroupTool["Circle Search1"]` 取得子模块，把它交给 `VmRenderControl.ModuleSource`，再调用 `mGroupTool.Run()`。
- 窗体关闭时调用 `mGroupTool?.DestroyGroup()`。

逐成员证据写入 `analysis/full-audit/batch1-20261107/A01/shipped-group-control-source-evidence.json`。这补齐了样例宿主的调用顺序和清理边界，但不把宿主代码误当成 Server 回调时序，也不证明本地实现已经具备同样的独立 Group 加载能力。

设计器源码还确认 `VmSingleModuleSetConfigControl` 和 `VmRenderControl` 在 `InitializeComponent` 中先创建，两个 `ModuleSource` 初始为 `null`。`Program.Main` 通过 `[STAThread]` 启动 `Form1`，初始化异常统一转换为 `VmException` 的十六进制错误码。
