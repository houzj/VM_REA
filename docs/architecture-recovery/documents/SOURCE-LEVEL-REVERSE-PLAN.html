1. 目标与执行原则

每个功能从原厂入口追到结果与释放：具体类型/成员 → 配置资源与绑定 → 参数读写 → 模块 → SDK/原生算法 → 输出与显示 → 保存恢复/销毁。实现必须能对应到这条链上的证据。

  1. 优先复用身份匹配的现有反编译源码；缺失部分通过REA取得托管方法、资源、原生伪代码与必要汇编。不要因已有独立实现能运行就停止查原厂。
  2. 托管反编译可接近源码；原生伪代码不是原始源码，类型、签名、别名、循环与浮点顺序须按需要核对汇编。禁止把自动生成的函数名当作功能证据。
  3. 不凭功能名称、常见算法、UI外观、测试期望或用户描述补行为。尚未查到的分支标记未知并建立后续取证任务。
  4. 静态源码已能回答的问题先完成静态追踪；探针只解决ABI、间接调用、实际路径、生命周期、精度等具体未决问题。每个探针必须有对应源码问题，避免不断扩样本却没有调用链进展。
  5. 逐结论区分：源码确认、运行确认、待核推断、独立实现选择、未知。运行确认不能伪装源码确认；独立替代不能伪装原厂算法。
  6. 不通过放宽容差、预置历史内存、跳过失败样本获得通过。不以通过率代替分支覆盖，不声称有限样本证明完整等价。

5. REA获取源码的操作规范

  1. 先按目标哈希检索已有源码/证据，登记已覆盖方法；只导出缺失或存疑部分，避免重复全量分析。
  2. 托管程序集使用可用的inspect_managed_artifact、inspect_managed_members及边界检查工具；同时取得相关XAML/BAML/XML、语言和图像资源。方法体、属性通知、命令、转换器与订阅解绑均须查到。
  3. 原生目标先选择身份匹配的现有分析状态；需要新目标时用open_binary。按实际可用schema调用analyze_function/batch_decompile、引用追踪及read_function_instructions，从模块入口走到真实callee。函数指针、虚表、导入桩、尾调用须展开。
  4. 反编译参数数量、类型或控制流存疑，查看调用点汇编与寄存器活性，必要时定点记录入口寄存器/栈。禁止再次因wrapper仅写RCX便认为RDX/R8参数丢失。
  5. 保存目标身份、函数地址、反编译文本/汇编、REA Evidence ID（若有）、导出路径和哈希。旧本地源码无Evidence ID时如实标“既有导出”，不能补造ID。
  6. 每组使用自己的输出目录；涉及REA活动目标的调用先协调所有权。不得并发切换同一活动session；确需并行时使用工具支持的隔离会话/私有工程，不假定会话隔离天然存在。
  7. 搜索无结果记录所查目标、范围和工具限制，不能写成该功能不存在。分析工具无法恢复的部分明确列为未恢复，不按意图续写。
