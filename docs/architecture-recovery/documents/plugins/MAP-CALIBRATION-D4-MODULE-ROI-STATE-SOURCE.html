D4 空 ROI 跨轮状态与清理有限切片（2026-10-19）

结论必须区分两种“无ROI”：正常类型1消息生成全图矩形，下一次完整双图运行会调用SDK setter替换旧ROI；ResetRoiData后没有有效条目或RoiFix不支持的raw类型，则会产生空shape向量，ProcessAlg跳过setter，旧SDK ROI指针不会由这些模块路径主动清除。DeInit会销毁SDK工具，从而释放两侧clone。

仅源码/汇编取证，无构建、原厂运行、共享产品修改。用户最新总进度口径为完整标定工具数/10，当前0/10=0%；内部D断点仍5/32，不作为总体完成度。

配置解析和正常全图路径

SetParam23870的RoiType_0/1路径分别调用22ec0(rawSide)再1f390。22ec0把type设1，将三组raw条目vector的end退回begin，并清raw几何字段；不销毁模块缓存shape、不清工作shape向量、不调用SDK setter、不销毁SDK工具。

Analyze1f390正常case1：写归一化矩形 center=(0.5f,0.5f), size=(1f,1f), angle=0，push入临时矩形条目vector，计入有效条目；成功末尾复制条目到raw ROI并写type1。因此正常全图消息并不留下“type1但无条目”。case2需要完整0x16字节矩形消息，case3需要0x1a字节扇环消息；只按当前有限空ROI问题核长度门，不展开其余几何算法。

case0xff经模块槽+58实际调用15830。其非空raw结构分支构造同一全图矩形，先经槽+50调用一个base helper，返回0才push矩形并设type1；该helper内部未在本切片展开，不能把0xff视为无条件全图。Init槽+60实际15660在create cause!=2时读取外部默认配置文件，逐项调用模块SetParam；外部默认配置读取成功与具体条目另需原资源/返回值，不可说Init必然保留或必然覆盖旧ROI。

Analyze本身空指针分支返回0xE0000001；但SetParam入口先拒绝null名称/载荷，不会因此进入ResetRoiData，不能把该直调Analyze分支当SetParam先清raw的可达路径。非null载荷进入ROI分支后，没有有效条目时返回0xE0000018；不支持消息码分支0xE0000514。这些解析失败之前SetParam已ResetRoiData，不能描述成完整保留旧raw条目。此时SDK旧clone与raw配置状态可能不同。

Process、取图和RoiFix

GetInputImage203d0只获取两侧图像、创建/更新对应IMvdImage、写到帧标志/物理点字段；在可见体中无SDK ROI清除、无工作shape向量或raw ROI重置。

Process21690：无新图早返；只到一帧则保留pending并写等待状态；两侧凑齐且像素类型检查通过后，依次调用RoiFix(source,0)、RoiFix(target,1)，随后调用ProcessAlg。asm21a12/21a27之后不测试EAX，直接跳21b94再调ProcessAlg，故不能假设RoiFix错误会自动阻止SDK运行。

RoiFix22f40入口无条件令 end(side)=begin(side)。后续仅：

  • raw type1/2且矩形条目非空：按条目更新/创建缓存矩形，push shape指针；中心/尺寸由图像宽高乘raw归一化值，角度字段传原shape setter。
  • raw type3且扇环条目非空：更新/创建缓存扇环并push。
  • 对应条目为空、其他raw type：不push默认形状，返回0。多形状type0x80等不在本函数支持分支，不能按泛型ROI解析器的支持面外推Map运行支持。
  • shape创建失败：返回其错误码；如果首条未push就失败，该侧仍为空；已经push的条目不在此处回滚。本切片不新增失败分配执行。

ProcessAlg21e46..21e9b：该侧工作向量数量为0即跳过相应setter；非0只传首指针。前面的两个SetImage不会顺带清ROI：同hashSDK原PE1a90写image字段+10并置dirty字节+8=1，1b50写目标image字段+28并置dirty字节+9=1，随后RET；完整原字节记录在索引，不能把这两个setter简化成“只写image”。模式setter3330只写模式字段+8。SDK Run3e30复用既有basic参数对象，不重建双图参数，47f0读取其ROI并可清dirty字节；已有C中无清双图ROI字段的写回，不能把dirty清0当ROI销毁。

DeInit、ResetMember与析构

DeInit1fae0实际asm：两轮循环销毁各侧模块image；销毁缓存shape（+17310/+17318、+17320/+17328）并将其指针置0；将工作shape向量end退回begin。随后1fb65..1fb77加载SDK工具指针+16598到RCX，经IAT2e4c8调用DestroyMapCalibToolInstance，再把该指针置0；释放两侧文件缓冲后，1fbc9 JMP 22d50 ResetMember。

SDK wrapper DestroyMapCalibToolInstance1070调工具虚析构；3990→4670销毁算法handle并对basic参数调虚析构；basic32a0→双图19c0→19f0释放两侧SDK clone。故模块缓存shape与SDK clone是两次不同层级的销毁，不把同一API名等同同一个地址。

ResetMember本身不调SDK ROI setter/null、不销毁工具；它清状态、路径、raw ROI条目、模块缓存shape指针等。新asm确认其完整续段，不能使用本次被memset误截断的新C。它的原厂静态入边包括Init的CALL21380及DeInit的尾JMP1fbc9，纠正旧审计“仅Init调用”的结论。Init若已有SDK工具，不重建它；但其后默认配置加载可能经SetParam变更raw ROI，因此不承诺重复Init后的最终ROI值。

模块析构1f280先调用DeInit，再析构两组工作shape向量与raw ROI容器，最后基类。DeInit的image销毁后此体没有将对应image字段置0；没有运行DeInit后复用同一模块对象，不能额外承诺这种调用序列安全。
