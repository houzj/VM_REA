# VisionMaster 高保真本地逆向实施总方案

## 1. 目标与完成定义

本方案把 VisionMaster 的本地重建拆成可复核的源码恢复、运行取证、实现、差分和主机验收链路。目标是形成一个能够在本地独立启动、创建和打开方案、配置工具、执行流程、显示结果、保存重开、停止释放并覆盖选定工具范围的重建系统。

“高保真”按操作和数据流定义。窗口截图只能作为差异信号，不能作为行为规格。每个已关闭功能必须能回答入口、调用成员、输入字段、状态变化、输出、失败传播、释放和持久化这八个问题。不能确认的行为保留为“运行未确认”，不能用常见产品意图补齐。

完整交付分为三个层级：

1. **范围完整**：明确本轮覆盖的框架单元、工具、方案格式、入口和设备边界。
2. **证据完整**：每条必需操作拥有可定位的原件、资源、CIL/汇编或受控运行证据。
3. **实现完整**：从启动入口到结果和释放形成闭环，并通过独立回归、主窗口操作和原厂差分门禁。

没有匹配原厂环境时，可以关闭源码和独立实现阶段，不能把原厂差分阶段写成已完成。

## 1.1 保真度纠偏前置阶段

现有实现中存在独立实现与原厂行为差异较大的区域。此前的自动回归主要证明当前合同和代码的内部一致性，不能证明 VM 保真度。后续先执行保真度重审，再扩展工具覆盖。

纠偏期间冻结以下行为：

- 不继续以“已实现工具数量”扩大主界面和工具目录。
- 不把独立 JSON 方案、托管 Blob、Group 合同或启动壳通过测试的结果写成原厂等价。
- 不用截图直接改样式，先回到原厂 XAML、资源、绑定、事件和运行状态证据。
- 不删除历史实现和证据，给每条现有实现追加 `fidelity-status`、差异、原厂证据和处理决定。

保真度审计先覆盖四个用户已经观察到差异最大的区域：启动/方案管理、主窗口导航与工具载体、执行/停止/结果链、配置/ROI/显示链。每个区域先建立原厂对照矩阵，再决定保留、重写、隔离或标记未知。

## 2. 不可变原则

### 2.1 证据优先

- 原件路径、版本、文件长度、SHA-256、MVID、PDB CodeView 身份必须固定。
- 反编译源码只证明托管控制流和成员关系。涉及 native、指针、虚表、寄存器和栈参数时必须补 PE、汇编或 ABI 证据。
- 运行探针必须保存输入、参数、区域、缓冲、结果、退出码、实际装载模块和日志哈希。
- 原厂运行、独立实现、主窗口操作和人工验收分别记录，不能相互替代。

### 2.2 结论分类

每条结论只能属于以下一种：

- `source-confirmed`：原始源码、资源或明确的静态调用边直接支持。
- `native-confirmed`：PE、汇编、ABI 或原厂 native 运行证据直接支持。
- `runtime-confirmed`：匹配身份的受控运行得到可重复观察。
- `independent-implementation`：当前实现为了闭合独立合同做出的选择。
- `unverified`：证据不足，保留问题和解除条件。

### 2.3 交付节奏

先整块设计和差异分析，再按垂直切片集中实施，最后统一构建、回归和对照审核。不得因为一个原厂方案缺失而停止不依赖它的源码恢复，也不得把静态切片数量当作完成率。

### 2.4 双项目边界

`main` 负责主窗口、工具发现入口、画布、流程和方案、Group、调度、公共数据合同、启动和持久化。`tool-plugins` 负责具体工具算法、工具专属参数、资源、控件、后台、native 适配和工具差分。公共合同只能有一个提交所有者，跨项目接口写入 `docs/CONTRACT-REQUESTS.md`，不复制另一工作树的未提交代码。

## 3. 证据等级和门禁

### 3.1 证据等级

| 等级 | 名称 | 可证明内容 | 不能证明的内容 |
|---|---|---|---|
| E0 | 身份清点 | 文件、版本、哈希、资源键、环境 | 成员行为 |
| E1 | 静态源码链 | 类型、成员、字段、分支、调用顺序、资源载体 | 实际实例状态和像素结果 |
| E2 | ABI/PE 证据 | RVA、虚表、寄存器、栈、导入、装载路径 | 宿主是否经过该分支 |
| E3 | 受控运行证据 | 输入、状态、错误、输出、生命周期和重复性 | 另一版本或另一环境的结果 |
| E4 | 独立实现证据 | 当前代码合同、测试和可重复结果 | 原厂语义等价 |
| E5 | 主机验收证据 | 用户可操作的入口到结果和关闭释放 | 未覆盖的工具或原厂差分 |

### 3.2 关键路径最低门槛

启动、方案容器、执行、停止、结果、保存重开和工具配置属于关键路径。关键路径必须达到：

- E0 身份固定
- E1 调用链闭合
- E3 或 E2+E3 的运行证据
- E4 独立实现回归
- E5 主窗口操作验收

原厂差分结论还必须增加匹配原厂身份和同输入证据。只有 E4 的功能标为独立实现，不能标 VM 等价。

### 3.3 每个单元的八个 S 状态

每个框架单元或工具按以下状态推进：

| 状态 | 退出条件 |
|---|---|
| S0 范围冻结 | 入口、版本、责任文件、依赖和未知项固定 |
| S1 原件身份 | 原件、资源、输入和工具版本有哈希 |
| S2 源码索引 | 成员/token/RVA/资源键和入口到出口路径完成 |
| S3 分支与生命周期 | 字段读写、条件、失败、停止、释放和持久化边界明确 |
| S4 实现设计 | 接口、深模块 seam、适配器、兼容策略和禁止猜测项明确 |
| S5 实施 | 代码和资源完成，独立实现与公共合同一致 |
| S6 自动验证 | 正常、失败、边界、重复、保存重开和资源释放通过 |
| S7 主机/差分验收 | 主窗口操作和原厂同输入差分达到范围门槛 |

S6 通过不自动关闭 S7。原厂运行受阻时保留 S7 未确认，继续推进不依赖原厂的 S0-S6。

### 3.4 保真度状态

每个现有功能另加一列状态：

- `parity-closed`：原厂源码/资源和运行结果均对齐。
- `source-shaped`：调用链和数据形状按原厂恢复，运行差分未闭合。
- `independent-contract`：当前独立合同完整，原厂语义未证明。
- `visual-only`：只完成外观近似，交互和数据流未闭合。
- `divergent`：已观察到与原厂的具体差异，等待纠偏。
- `unknown`：缺少足够证据，禁止继续推断。

只有 `parity-closed` 才能在对外报告中称为原厂高保真。`independent-contract` 和 `source-shaped` 仍属于阶段性成果。

## 4. 目标架构和深模块 seam

重建系统按深模块设计。每个 seam 对调用方提供少量接口，内部隐藏状态机、持久化、错误和资源释放。接口不仅包含类型，还包含顺序约束、错误模式、配置要求、生命周期和性能边界。

### 4.1 启动模块

接口：`Start(args, environment) -> StartupContext`。内部处理工作目录、单实例、开发认证替身、原厂服务状态、欢迎页、方案选择和主窗口所有权。启动异常必须落盘并显示日志路径，不能静默退出。

### 4.2 方案模块

接口：`Create / Open / Save / Close / EnumerateRecent`。内部处理格式版本、路径、资源目录、迁移、失败回滚、最近列表和未保存状态。原厂 `.sol` 与独立 JSON 使用不同适配器，未确认格式不能伪装成兼容。

### 4.3 流程执行模块

接口：`Run / Stop / Observe / GetResult / Release`。内部处理执行所有权、回调、取消、结果缓存、子流程、Group、错误传播和资源收尾。所有调用方通过同一执行合同，禁止各工具自行实现第二套生命周期。

### 4.4 配置和交互模块

接口：`Describe / Load / Edit / Validate / Commit / Restore`。内部处理参数模型、模板、ROI、Mask、显示、二进制载荷、订阅和失败恢复。工具专属 UI 只实现适配器，公共交互合同归主框架。

### 4.5 原生适配模块

接口：`Create / SetInput / SetParam / Run / ReadOutput / Destroy`。内部保存 ABI 参数、虚表偏移、装载依赖、编码、错误码和内存所有权。没有 ABI 证据的参数保持不透明，不通过清零或硬编码制造等价假象。

### 4.6 证据模块

接口：`CaptureIdentity / CaptureTrace / Compare / PublishReport`。内部统一保存原件清单、探针输出、哈希、调用路径、差异、未知项和复跑命令。产品程序集不放截图或取证逻辑，取证工具集中在 `tests`。

## 5. 垂直切片顺序

横向铺满所有 UI 或所有工具会制造大量未验证壳层。实施按以下垂直切片推进：

| 切片 | 闭环 | 依赖 |
|---|---|---|
| VS0 | 无方案启动 → 欢迎页 → Guide → 空载主窗口 → 关闭释放 | 原件身份、启动合同 |
| VS1 | 新建方案 → ImageSource → 加载本地图像 → Binary/Blob → 结果 | VS0、数据类型、执行合同 |
| VS2 | VS1 方案保存 → 退出 → 重开 → 结果和资源恢复 | 方案模块、资源目录 |
| VS3 | 工具箱 → 拖放 → 配置 → 参数提交 → ROI/显示 → 执行 | 公共配置模块 |
| VS4 | Group → 子流程 → 循环/分支 → 结果投影 → 停止 | 执行和数据合同 |
| VS5 | 失败输入 → 错误传播 → 停止 → 资源释放 → 再运行 | 生命周期和错误合同 |
| VS6 | 原厂方案身份 → `.sol` 读取 → 场景直启 → 原厂结果差分 | 匹配原厂环境和方案 |
| VS7 | 一个真实工具完整主窗口路径 → 复用公共合同 → 保存重开 | 工具专属证据 |
| VS8 | 工具批次覆盖 → 共享合同稳定 → 分类、目录和外壳入口 | VS7、工具清单 |

每个切片都必须留下源码路径、状态机、测试入口、产物身份和未覆盖边界。

### 5.1 保真度重审切片

在继续 VS6-VS8 前，追加以下纠偏切片：

| 切片 | 对照内容 | 交付 |
|---|---|---|
| FR0 | 当前构建与原厂启动截图、窗口尺寸、资源、状态转移 | 差异清单和证据等级 |
| FR1 | 原厂启动 → Guide → 新建/最近/打开 → 主窗口 | 启动与方案状态机 |
| FR2 | 工具载体、工具箱、配置窗口、参数提交和结果显示 | 工具入口与公共合同差异 |
| FR3 | ImageSource → Blob/真实工具 → Run/Stop/Result | 同输入数据流和第一处分歧 |
| FR4 | 保存、重开、错误、停止、释放和再次运行 | 持久化与生命周期差异 |

FR0-FR4 没有达到 `source-shaped` 前，不扩展更多工具 UI；没有达到 `parity-closed` 前，不改写原厂等价结论。

## 6. 分阶段实施路线

### P0 建立证据基线

任务：

1. 冻结主线和工具线 HEAD，记录工作树差异。
2. 建立 VisionMaster 安装根、所有 DLL、SDK、PDB、资源、样图和方案清单。
3. 为每个原件建立版本、长度、SHA-256、MVID、导出和依赖记录。
4. 建立受控运行机器清单和桌面/权限/设备前置条件。
5. 为历史输入、参数、ROI/Mask、像素格式和结果定义固定样本。

退出：所有后续任务能引用唯一身份。缺失原件记录解除条件，不用“文件不存在”证明功能不存在。

### P1 源码恢复和架构图

任务：

1. 从入口程序集开始恢复 Program、App、启动服务、主窗口、方案、流程、执行和结果成员。
2. 用 token、RVA、CIL、反汇编和资源键建立调用边。
3. 恢复所有字段读写、分支谓词、事件订阅、回调消费者和释放路径。
4. 对 native 调用记录真实入口寄存器、栈参数、虚表槽和装载模块。
5. 把每条边标记 `source-confirmed`、`native-confirmed` 或 `unverified`。

退出：关键路径从入口到结果和释放无断边。仍缺的方法体列入取证清单，不能进入实现猜测。

### P2 公共合同和执行核心

任务：

1. 固定数据类型、端口、动态 IO、Region/Mask、Fixture、数组和复合叶合同。
2. 固定方案/Procedure/Node 的身份、版本、位置、连线和资源引用。
3. 固定 Run、Stop、Cancel、Callback、Result、Error 和 Dispose 顺序。
4. 建立可替换的执行适配器和唯一执行所有权。
5. 用 ImageSource → Binary/Blob 完成 VS1。

退出：至少一个真实工具消费公共合同，普通路径和失败路径均可重复。

### P3 启动、方案和主窗口

任务：

1. 对照原厂 WelcomeDialog、GuideWindow、AppAfterStart 和 ShowMainWindow。
2. 完成空载启动、单实例、工作目录、认证替身、日志和关闭释放。
3. 完成独立 JSON 方案创建、保存、重开、最近列表和资源目录。
4. 建立原厂 `.sol` 只读探针，不能在格式未知时写兼容实现。
5. 完成主窗口工具箱、画布、流程 Tab、结果和错误面板的空载操作。

退出：VS0、VS2 通过。`.sol` 和场景直启单列为原厂门禁。

### P4 配置、ROI、显示和订阅

任务：

1. 根据原始模板和参数成员恢复普通配置编辑器。
2. 恢复数值、枚举、布尔、文本、数组、二进制和动态参数的读写。
3. 恢复 ROI、Mask、全屏、图像尺寸、显示开关和失败恢复。
4. 恢复订阅、结果显示、调试会话和节点级执行。
5. 以一个真实工具完成配置到运行的 VS3。

退出：所有公共交互合同有来源、实现、测试和至少一个真实工具消费。

### P5 Group、子流程和复杂数据

任务：

1. 恢复 Group 节点身份、子流程、输入输出、引用和保存格式。
2. 恢复 Loop、Branch、Break、累加、数组和复合叶的生命周期。
3. 恢复 Group 内配置、ROI、结果投影和错误/停止传播。
4. 建立嵌套、重入、取消、异常和释放回归。

退出：VS4、VS5 通过。无法确认 native 复杂数据时保持透明容器，不清零或硬编码。

### P6 工具批次实施

工具按依赖和证据批次推进，不按目录顺序盲目铺开：

1. 先 ImageSource、ImageBinary、Blob、Fixture 和 Branch 作为主线消费工具。
2. 再推进标定、坐标、定位、测量、识别和缺陷工具。
3. 每个工具先完成源索引和公共合同需求，再做专属实现。
4. 每批至少一个真实主窗口路径，覆盖配置、运行、停止、结果、保存重开。
5. 162 个目录工具逐批建立身份、依赖、入口和未确认项，清点不计源码闭合。

### P7 原厂同输入差分

任务：

1. 在匹配原厂环境固定宿主、模块、SDK、方案、样图和参数哈希。
2. 宿主和直接 SDK 各独立运行至少两次。
3. 比较输入像素、活动 ROI/Mask、Run 前缓冲、完整结果向量、BinaryImage、BlobImage、错误码和释放顺序。
4. 找到第一处分歧后再归属公共框架或工具专属实现。
5. 每次修改只针对已证实的行为，修改后重跑正例、负例和保存重开。

退出：报告指向首个可重复差异、准确调用边和证据。证据不足时根因保持开放。

### P8 全域覆盖和发布

任务：

1. 运行全量无界面回归和身份审计。
2. 运行关键垂直切片的主窗口验收。
3. 对每个工具生成源码、实现、运行和差分退出矩阵。
4. 生成构建产物、复跑命令、哈希、已知限制和回滚点。
5. 由用户决定提交、推送和两项目同步时点。

退出：选定范围满足完成定义，未覆盖范围和原生未知项公开列出。

```text

当前分类：source-confirmed / native-confirmed / runtime-confirmed / independent / unverified

```

任何任务卡缺少原件身份、入口、退出条件或复跑命令时，不得进入实施。

## 8. 自动化验证矩阵

每个垂直切片至少包含：

- 正常输入和空输入
- 参数下界、上界、非法值和缺字段
- ROI/Mask 为空、全屏、部分区域和图外区域
- 重复执行、停止、取消、异常订阅者和资源释放
- 保存、退出、重开、版本迁移和路径变化
- 缺插件、版本不匹配、依赖缺失和错误传播
- 输入缓冲、结果向量、显示缓冲和错误码哈希

测试只证明当前实现的合同。原厂等价必须有匹配原厂证据。截图和人工反馈记录为差异线索，不直接成为实现规格。

## 9. 高风险问题和门禁策略

| 风险 | 处理方式 |
|---|---|
| 原厂方案缺失 | 继续源码和独立实现，原厂差分保持打开 |
| 宿主 DLL 版本不匹配 | 先恢复身份，不比较数值 |
| native ABI 参数不清 | 记录寄存器/栈/虚表，禁止按反编译签名猜参数 |
| 主窗口看似可用但流程不执行 | 优先检查执行合同、数据类型、订阅和资源生命周期 |
| 测试通过但 VM 行为不同 | 维持 independent 分类，要求原厂同输入证据 |
| 两工作树共享文件冲突 | 只允许一个提交所有者，使用合同请求交接 |
| 编译输出被进程占用 | 使用独立 OutDir、关闭自有进程、保留用户进程 |
| 资源缺失或路径错误 | 建立资源清单和启动前资产预检 |
| 任务过大导致半成品 | 继续切成单入口垂直切片，每片 3 项以内验收条件 |

## 10. 交接和发布格式

每次交付必须包含：

1. 变更文件和唯一提交 SHA，或明确说明当前未提交。
2. 原件、源码、资源、探针、产物和报告的路径及哈希。
3. 实际执行的构建和测试命令。
4. 通过的检查数量只作为证据，不冒充完成率。
5. 源码确认、独立实现、运行确认和原厂差分分别给出状态。
6. 未完成项、阻塞条件、最小解除条件和复跑方法。
7. 用户需要人工验收的具体路径、操作步骤和预期现象。
