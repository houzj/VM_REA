更新：2026-10-17。**当前 `main` 兼任集成管理者**，不建立第三份产品代码项目。本文是两线的协调基准；涉及节点配置的职责以此处的新划分优先于 `PARALLEL-WORK.md` 中“所有共享契约都在框架线修改”的旧句。插件线的 `docs/PLUGIN-FRAMEWORK-CHECKLIST.md`（PF-001～014）是该线详细任务表；其当前内容有未提交改动，**尚未合入 main**。本文件不修改插件工作树，也不代表已通知或指派另一个对话。

## 管理者如何分配与验收

| 管理事项 | 唯一负责方 | 交付规则 |
|---|---|---|
| 跨线任务登记、冲突裁决、版本基线、集成验收、发布与 `main` 推送 | 当前框架/集成线 | 为每项指定主责、协作、原生证据、接口版本、提交号、验证层级和剩余差异；没有已提交代码时只登记在制状态 |
| 原生节点配置公共架构、配置模型和生产控件模板 | `tool-plugins` 插件线 | 用户已明确授权插件线修改**其工作树内**必要共享代码；提交后由 main 审核合流，不在 main 同时做第二套配置宿主 |
| 工具算法、独有参数、专属内容控件/操作适配器、工具依赖与原厂差分 | `tool-plugins` 插件线 | 每个工具保留自己的证据、真实运行数据与 UI 验证；工具代码不得自造第二个公共窗口/调度/订阅体系 |
| 工作流画布、节点位置/连线/交互、Tab/工具箱外框、Group、流程/方案所有权 | `main` 框架线 | 继续使用现有流程与 Group 契约；涉及节点配置入口的交叉文件先冻结，按合流窗口审阅 |
| 插件发现、注册、原生目录与框架工具箱映射 | `main` 框架线主责，插件线提供清单及工具元数据 | 原生 `ToolBoxData.UpdateLoad` 从工具目录读取 `ToolItemInfo.xml` 并按分类排序；`IMVSGroup.LoadAssemblies` 展示模块程序集搜索。当前项目仍是硬编码注册和静态目录，**尚未完成动态发现**；插件线 PF-012 不再另做第二套加载器 |
| 数据类型、动态端口、复合叶、订阅执行和 ROI/Fixture/Polygon 的交叉契约 | 本轮按下表逐项锁定文件负责方 | 插件线有用户授权的在制共享改动；主线已有复合与 Group 实现。先比对提交基线与数据形状，再合并，禁止用复制未提交文件覆盖任何一方 |

两线可以并行逆向**不同原生证据**，但同一原生控件/状态机只设一个功能主责。用户反馈记录差异，不代替原生源码或受控运行依据。声明“已完成”必须同时说明源码确认、托管实现、实际产品操作、原厂同状态差分四级证据，缺一项就标该级未验证。

## 合流闸门与任务状态

1. 插件线完成 PF 子项与至少一个真实工具迁移，保存原生路径/哈希、接口差异、可运行证据；按用户要求先构建并留人工验收，再以中文提交和推送其分支。**当前未提交在制文件不能直接挑选或当作已交付。**
2. `main` 只在交付提交出现后比对两线基线和受影响文件，先合公共合同，再合宿主，最后注册一个真实插件。必要时在 main 做增量适配，不整文件覆盖。
3. 在实际主窗口完成“工具箱出现→拖放→配置→订阅/ROI→运行/停止→结果/错误→Group内调用→保存重开→关闭释放”。检查结果数值与 UI 状态；测试通过、离屏截图和原厂差分分别记录。
4. 主线更新框架验收表并发布人工验收版本；保留尚未复现的原生数据类型/ABI、设备服务和模板差异。两线中文提交各自工作树，只有主线负责最终 `main` 集成推送。

不额外创建“管理者代码项目”：上述清单和合流闸门就是管理入口。若以后需要专门的协调对话，也应只读取两线状态与维护任务表，不持有第三套可编辑产品源码。
