阅读与迭代说明：先分析自研，再由逆向证据驱动开发

当前是持续迭代的开发资料：本次以已有代码和已取得的逆向材料为边界，交付现状分析、明确缺口、证据入口和有依据的方案。未实现项后续开发时补充，待核实项取得材料后复审；不要求本次还原全部VM行为或写成最终状态。新增材料只更新受影响条目，记录证据、结论和建议的变化。

推进顺序：先分析与优化自研现状，再由逆向驱动后续开发

第一阶段 · 正向分析与优化方案：以自研实际源码为主，按主界面和工具界面入口梳理数据结构、参数快照、调用与状态转换、异常取消、缓存和释放；逐项指出已实现路径的缺点，形成具体接口、职责、数据合同及验收改法。有现有VM材料则作为参考，缺少VM实现不阻止明确的自研问题形成整改方案。阶段产出是可供开发评审的现状、缺陷、方案、源码依据和待证边界，不能只列未实现清单。

第二阶段 · 逆向证据驱动正向开发：按实际开发需求补充原函数及上下游、数据格式、状态和寿命证据；复核后决定借鉴、混合优化或新增，更新对应方案，再在获准实施时修改产品并验收。逆向材料未到不填造最终设计，材料已到不自动视为已核实。本轮授权仍限文档，不实施产品改动。

实现状态怎么读 · 开发时怎样找依据

已实现：仅表示所列代码路径存在，仍须阅读局限；部分实现：已有路径与缺失环节分别列出；未实现：保留为后续开发项，不把提案当现有代码；待核实：材料不足，不能判断有无或优劣。当前无独立工具声明，也不等于底层没有可复用能力。

开始具体开发前：从主界面或工具入口定位能力 → 阅读自研实际数据结构、调用链及异常/释放路径 → 查看双方来源的文件、方法、行号与SHA → 查看VM恢复模型对应入口 → 根据“仍需补充的原实现”取得缺少代码 → 复核推荐取舍、改法及验收标准。VM资源声明只能证明字段或入口；原生行为未恢复时继续标待核实，不补写推测。

停止与收尾：请求不等排空，登记不等释放

当前停止菜单发请求后立即置IsRunning=false并记录“已停止”。关闭路径的StopAndWait轮询宿主活动登记；引擎finally仍只释放剩余租约，没有等待全部running Task。三个层次不能互相代证。

立即宣告已停止：此方法立即IsRunning=false并记录已停止，属于已证缺陷，不是推荐设计。（src/UI/Shell/Windows/MainWindowViewModel.cs:2188）

取消信号传播：会话创建时链接调用方取消Token；该边是取消信号关系，不声称管理器直接调用RequestStop方法。不同入口的取消及观察仍需统一。（src/Workflow/WorkflowRunSession.cs:29）

finally先释放租约：当前finally枚举仍在running的项释放Lease，没有await它们结束；图画的是退役缺口。（src/Workflow/WorkflowExecutionEngine.cs:399）

六条入口链：事实、VM参考和具体改法在同一处

启动：谁把系统组装起来？

App.OnStartup → Infrastructure.PluginManager.LoadPlugins(path) → ToolRegistry → ServiceInitializer → SolutionManager → MainWindow

当前源码实际怎样

实际启动使用Plugin.Infrastructure命名空间的PluginManager，先装载插件再进入可能序列化参数的服务。Core也有同名旧管理器，不能按文件名把两条链拼起来。

VM可参考什么，还有什么未知

VM只作恢复模型的启动/全局入口参考；本页没有把其DLL布局复制成自研层次，也没有据原目录判断发行完整。

具体改法与适用理由

先把装配职责/缺依赖错误写清；发现、类型注册、实例创建和ready状态分开。不要仅改目录或把LoadPlugins无参日志当加载成功。

怎样验收（本轮未运行）

插件缺失/类型加载失败/参数反序列化失败各有明确阶段；失败不暴露半初始化主界面；干净部署另行运行验证。
