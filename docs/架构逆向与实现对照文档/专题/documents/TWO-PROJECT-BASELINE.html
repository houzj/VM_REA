统一顺序

  1. 双方先以 职责边界、主框架清单、插件工作树的 PLUGIN-FRAMEWORK-CHECKLIST.md 和 接口登记 作为相同开发协议。此步骤不改变代码分支。
  2. 插件工作树保留当前未提交候选。用户完成其要求的人工验收后，由插件对话按闭合功能中文提交并推送；失败项继续保留在其工作树，不通过强制提交来制造“统一”。
  3. 用户决定集成时，先比较两分支在 Contracts.cs、GraphExecutor.cs、GraphValidator.cs、WorkflowSubscriptions.cs、MainWindow.xaml.cs 和插件配置宿主的差异。针对每项接口选一个提交所有者，按字段/方法增量合并，不能整文件覆盖。跨流程身份与流程等待时间分别按 FCR-013/014 核对。
  4. 在 main 对一个真实工具走通“发现→拖放→配置→订阅→执行/停止→结果→Group→保存重开→关闭释放”，并重跑两线相关检查、保留原厂未验证差异。用户确认集成节点后，再由两分支所有者把各自分支更新到该集成提交；届时记录相同的完整 SHA，才可称为统一代码基线。
  5. 统一后仍按各自目录独立开发；新跨界需求只写请求与验收样例，不在另一工作树直接修改。每次再合流重复第3—4步。

项目间的消息、清单和自动测试不是 Git 同步。停止在当前状态不会丢失任何在制文件，但插件项目尚不能安全地从 main 强制快进。本页也不把插件候选的测试通过当成人工验收通过。
