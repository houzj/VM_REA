2026-10-19。继四方向首轮报告之后的新增静态证据。只读已存反编译和 CIL，未实例化或执行厂商代码，未改产品、合同或 tool-plugins。以下路径相对仓库根；本轮原件哈希、逐行摘录位于 analysis/full-audit/undo-round2-20261019/。源码可达性不等于实际原机命中。

1. 参数捕获：第一次合法写入取旧值，首次 Undo 前取新值

analysis/decompiled/VMControls.WPF/VMControls.WPF.DataForUI/VmModuleDecorator.cs:242–278：打开配置先 Register RootOperation {RootOperType="ModifyConfig"}，随后 Show；关闭回调只 RemoveEmptyOperation。这不是每个控件值各建一根。

analysis/decompiled/Apps.XmlParser.CapabilityAudit/Apps.XmlParser.ParamTab/NameValueItem.cs:980–994 的 SetParamUnitDirect 将值写到 AlgorithmTabRoot.UserStringData，或父项 InnerSetStringParamValue；AlgorithmTabRoot.cs:650–653 保存传入 IParamsConfig。analysis/decompiled/VM.Core/VM.Core/ModuleParam.cs:39–49 非全局字符串 setter 先 RecordParamUnRedo，再 SDK 写入，再 OnModuleParamChanged。

ModuleParam.cs:128–155 的旧值最初是 Expression<Func<object>> () => Parent.GetModuleAllParams()。CanRegisterParam（204–224）按 ModuleFullName 查已存在的参数 part、拒绝重复，要求根为 ModifyConfig、拒绝 IVmProcedure，只有通过后才编译表达式取旧值。因此连续编辑同一模块并非逐字段快照。模型数据有独立同模块去重和捕获（166–197）。Group % 动态运行参数在 RecordParamUnRedo 首先返回，不能从普通参数链推导其可撤销性。

ParamUnRedoOperation.cs:12、26–35 初始 IsDataComplete=false。analysis/full-audit/mf04-unredo/VM.UnRedo.il:2865–2906,3085–3110 的 UpdateActionData 选出未完成 part，先置 true，再 Update；唯一直接调用在 Undo:2137，且在 Pop 前。ModuleParam.Param_Update:258–262 此时取 GetModuleAllParams，存 NewParamList；Undo/Redo:226–256 分别 SetAllParams，局部吞掉异常，非 Group 刷 ready。

VmModule.cs:3041–3045、3126–3135 进一步闭合到 SDK GetParamList/SetParamList；空列表不调用 SetParamList，Group 回放通知 IsEnableLoop。这里只确认调用/条件，未验证底层参数列表内容、复制隔离及错误时 SDK 实际状态。

新增异常推论：Update 若抛异常，Undo 的外层 catch 吞异常，根尚未移栈，但该 part 已被标完成，后续 Undo 不会由这一筛选再次采新值。不能宣称异常自动恢复或安全重试。本轮未通过厂商代码执行验证该推论。

2. 模块、Group、流程和方案不是同一种恢复载荷

普通模块 VmModule.Export:2926–2951 返回 ID/父ID/类型/名称及 pData+nDataLen，无磁盘路径；VM.PlatformSDKCS.Audit/VM.PlatformSDKCS/ModuleManager.cs:1069–1097 调 GetModuleExportData、转 managed 结构后释放 SDK 动态内存；ImvsSdkDefine.cs:2636 起构造以 IntPtr2Bytes 复制数据。恢复由 VmModule.Import_Module:5296–5305 定位父路径，进入 VmModuleSet.ImportModule:810–853：分配/复制 HGlobal、查已加载 Cs 类型、Import，finally FreeHGlobal。未闭合异常发生在 try 之前的资源释放及丢失父节点行为。

Group IMVSGroup.Export:112–159 使用 BaseDirectory/TempFiles 的 0.gro，冲突尝试 1..799；SyncExportGroupModule 后 VmModuleDataInfo.strPath 持文件名。恢复在 VmModuleSet.ImportModule 走 VmSolution.ImportFile(...,1u)，不是普通模块内存 Import。ModuleUnRedoOperation.cs:34–42 带 UpdateAction 的新增模块 part 初始不完整，Update_Module（VmModule.cs:5315–5333）重新 Export 并逐字段替换；删除模块路径则先 Export、后删除、注册完整 part（4183–4214）。Dispose（ModuleUnRedoOperation.cs:58–68）仅对路径含 TempFiles 且存在的文件删除。不能把它当通用安全目录校验。

流程 VmSolution.Export_Procedure:1661–1713 先删除 CalibData，采用 0 或 1..800 临时流程文件，等待原生导出结束；Import_Process:1649–1659 用强制忽略 global 的 ImportProFile(...,1u)，Path 为 null 则新建流程。路径耗尽/部分导出/原生恢复效果仍未知，不能把它称为无副作用快照。

方案 VisionMaster.Exe.Audit/VisionMaster.Project/ProjectManager.cs:382–413 用 UnRedoStackCount（默认15）分配临时 .sol；CreateNewSolution:419–482 创建 SolutionCreate 根及 oldSolution/newSolution 两 part。原方案已有路径时直接记路径，未在此复制：并非所有方案撤销均持不可变独立文件。

SolutionUnRedoOperation.cs:49–67 的 DeleteFile(object) 实际设置 TempPath，Dispose 比较 TempPath/Data.Path，避免删除新 part 仍引用的同路径。IL:1876–1950、2982–3036 表明 BuildPart 的 IDisposeTempFile 路径清 redo 时先把新对象交给旧 part，再 Dispose 旧根。名字 DeleteFile 不能按字面解释成即时删文件。

3. RecoverStack 已定位到密码取消，而非所有失败事务恢复

全反编译文本内搜索 RecoverCallBack，实际调用位于 ProjectManager.Redo_Solution:1042、Undo_Solution:1068。ValitPassWord:994–1030 返回用户取消状态；取消时调用表达式回退栈，再 return。IL RecoverStack:2387–2402 仅 source.Pop→target.Push，不回放数据、也不重置 BuildInStack 的显示状态。Undo 已在动作前移动 root 并 BuildInStack(false)，故不能把回调当整个撤销事务回滚。原机历史面板取消后的显示和多 part 后续执行仍需采集。

4. Group 编辑：真实命令与 SDK 写入到 Register 的静态链

DynamicObjectConfigControl/DynamicObjectConfigControl/DynamicRunParamConfigControl.xaml:25 绑定 ConfigCommand，并将 EditRunParamMethod 作参数；同名 xaml.cs:12–18、34–46 创建窗口、挂 DataContext、AsyncLoadParams、ShowDialog。Apps.XmlParser.ParamTab/GroupRunParam.cs:134,251–304 命令先清理孤立项，再 true→ShowDialog 委托→false，无 finally；忽略委托的 bool? 返回，不存在这里显式 Cancel 回滚。

该窗口操作持久化路径已由源码闭合：ParamConfigDataBase.ChangeGroupInfosToSDK:186–215 写 Owner.UserData[ParamGroupNamesList/ParamGroupIDsList]；AddParam:487–580 写参数索引/来源/HeadPath；DelUserDataByName:718–740 删除相应键，SetParamIndex:745–750 写索引。GroupRunParam.cs:54–58 确定这些 key 的来源。

VM.Core/UserData.cs:50–108 的 setter 对非全局数据仍 SetUIParamValue，再 RecordSingleData（非动态分支），或在动态模块 ModifyConfig 分支先 RecordAllUserData 后 SetUIParamValue；RecordSingleData:119–132 是不带 predicate 的 part Register；RecordAllUserData:109–117 带 CanRegisterUserData（155–176）并懒采集整个 UI 参数表。IsDataComplete/优先级/ParamRoot 首尾回放在 UserDataUnRedoOperation.cs:25–59 定义。

因此只要实际 Group Owner、Ioc 和窗口按此链装配，抑制期间仍会写 SDK，part 在服务 Register 被 ForbidBuild 拒绝；不是整个写入被拒绝。SetForbidRecord(true) 之前清孤立项可能已记录 part；若其后对话框逃逸异常，后续 false 和重建集合不执行，且已发生的数据写入不回滚。这些是静态条件结论，尚未记录真实 Group Register 命中、窗口内异常逃逸和实际根对象身份。

5. 下一步可隔离验证与 main 结论

本轮不适合直接改 main 的快照撤销模型：它缺少同模块 part 去重、首次合法旧值捕获、延迟新值捕获、SDK载荷及根类型，跳过 undo.Push 无法表达这些行为。可先在 tests 的独立模型实现以下状态序列，并明确是源码翻译模型，不能标作厂商运行结果：同模块两次写入只一次旧值读取；ForbidBuild 在 predicate 前拒绝 part；Update 抛异常时完成标记与根所在栈；新根无 part 时 redo 是否保留；Solution 密码取消回调仅移栈；同路径临时文件保护。

真正原机操作应只在独立复制的工作目录/TempFiles、指定实例里人工或被动调试：打开 Group 配置，在命令入口、UserData.Register 和 SDK setter 设断点，记录根身份、ForbidBuild、模块/key、动作数及前后UI数据；执行正常关闭/取消，再采空栈、旧根、新根和错误路径。不得在安装目录或已有任务实例直接构造 UnRedoSchedule（构造会清 TempFiles）。运行厂商程序集和主动注入故障不在本轮执行范围。

结论状态：参数捕获链、普通模块/Group/流程/方案的 managed 载荷和消费链、Group 命令到持久化 Register 静态可达性已进一步确认；实际 SDK 数据/Group 命中、故障及取消的原机结果未确认。没有新增产品补丁或运行等价声明。
