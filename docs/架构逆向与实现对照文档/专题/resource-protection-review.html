资源保护：XML、AES提供器与ZIP

三原件 SHA256/MVID、引用程序集身份及 22 个聚焦 CIL 方法静态核查。未加载或执行厂商程序集，未解密/改写资源；全链仍未关闭，浏览器呈现未验收。

BaseNode belongs to VM.Xml.dll; AesCryptHelper resolves by metadata to VM.Util.dll, ZIP helper to VM.Compress.dll. These identities match selected originals; runtime assembly binding remains unverified.

Aes string Encrypt: UTF8 → byte Encrypt → Base64. Decrypt: FromBase64String → byte Decrypt → UTF8.GetString → TrimEnd with a newly allocated single zero char array.

Byte operations call Rijndael.Create, set Key from a shipped UTF8 literal, set static MY_IV, then CryptoStream. No explicit mode/padding setters appear in these bodies. No claim about effective framework defaults or .sol cryptography.

Byte Decrypt allocates output equal to ciphertext length, calls Stream.Read once and discards count, returns entire array. Stream finally regions are present; Rijndael object has no explicit Dispose in these bodies.

BaseNode file load changes IgnoreUnknown before locking, sets file attributes before branch selection, decrypts only XML marker path, ZIP branch loads the returned stream directly. IgnoreUnknown=false lies after lock, outside finally; exceptions can bypass reset.

String/byte load overloads use loadXmlByString; that body parses and Init without marker decryption. Its failure wraps ex.Message and can bypass IgnoreUnknown reset.

Referenced ZIP helper calls DecompressToBytes; each entry gets Stream.Length-sized buffer, one Read whose count is discarded, then whole buffers are concatenated via BlockCopy. Entry names are not selected here. ZIP Length, reader dispatch and conditional CRC are recovered separately in zip-stream-review; underlying inflater/input-buffer and format combinations remain open.

Save(string) writes ToXmlStringWithHead output into relative temp.xml, disposes writer, deletes existing target, creates directory, copies temp, deletes temp. No Encrypt call in this save body; this is not proof of an inverse protected-resource round trip or all derived serialization behavior.

Original static IV initialization is now linked to a bounded 16-byte FieldRVA payload and its SHA256, matching the CIL InitializeArray token and both set_IV consumers. No provider execution or protected-resource round trip was performed.
