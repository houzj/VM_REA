<h2 id="重点追踪缓存图像跨运行状态链">重点追踪：缓存图像跨运行状态链</h2><p>原厂资源 <code>D:/Program Files/VisionMaster4.4.0/Applications/Module(sp)/x64/Collection/ImageBufferModule/ImageBufferModule.xml</code> 直接声明 <code>InputImage</code> 为 IMAGE Combination，子叶 <code>InImage/Width/Height/PixelFormat</code>，另有两个可选整数输入 <code>RefreshFlag</code>、<code>BufferCount</code>；输出 <code>ModuRunTime</code>、<code>ModuStatus</code> 和 15 个 <code>OutImageN</code> IMAGE Combination。<code>ImageBufferModuleAlgorithmTab.xml</code> 将两个整数配置绑定到 <code>ButtonSelecter</code>。这只证明<strong>声明与配置入口</strong>，不证明本轮已经重放原生 FIFO/异常分支。<code>docs/plugins/IMAGE-BUFFER.md</code> 历史记录的原生 <code>Process</code> RVA <code>0xde30</code>、<code>CopyImage</code> RVA <code>0xe6a0</code> 和 55 组 SDK 结果是检索索引；它引用的 <code>analysis/full-audit/image-buffer</code> 在此工作区不存在，因此本轮不得把它们标记为重新核验的源码或运行证据。</p>
<p>当前实际链为 <code>ToolNavigation.LoadToolCategory</code> / <code>MainWindow</code> 注册 → <code>GraphEditorDocument</code> 节点/连线 → <code>GraphExecutor.RunAsync</code> 收集连接或订阅并执行 <code>DataKinds.Coerce</code> → <code>ImageBufferPlugin.Runtime.ExecuteAsync</code>。运行体默认 <code>BufferCount=15</code>、<code>RefreshFlag=1</code>，先校验数量 <code>0..15</code>；刷新为 1 时读 <code>InputImage</code>，复制 Gray/RGB/Raw 的实际字节到 <code>ModuleExecutionScope.State(module,node)</code> 的队列，超过数量从队首弹出；不刷新则保留队列。成功时顺序发布 <code>OutImage0Image</code> 起的已占槽，另发布宽/高/格式与状态/时间；失败时发布状态/时间，但 <code>GraphExecutor</code> 在 <code>PreserveFailedOutputs=false</code> 时只记录失败，后继不见这些输出。后继连到未占的可选图像槽，<code>GraphExecutor</code> 按 <code>UpstreamUnavailable</code> 跳过。因而“原厂保留旧队列”和“当前流程中后继可见旧图像”不能画等号，须按同一运行序列分别测。</p>
<p><code>ImageBufferWindow.cs</code> 的输入源用宿主 <code>PickSubscription</code>、整数可输入常量或订阅；按钮触发 <code>context.Run</code>，连续运行和关闭停止由窗口自己维护。<code>ModuleExecutionScope.cs:34,41,44-48</code> 把状态按 procedure/module/node 隔离，删除节点/替换方案时清理；<code>GraphExecutor</code> 每次创建新的 runtime，但复用 scope 中的队列。这是<strong>当前独立实现</strong>，与原厂保存/加载队列及跨 Group 作用域不能从同名端口直接等同。测试和历史文档声称本地 FIFO/重载通过；本轮只静态核到路径，未运行新的原厂 SDK 或 UI 实例。</p>
<p>可证伪的下一次操作：在自有同一方案里用 RGB/Gray 混合帧执行 <code>ImageSource → ImageBuffer → 二值化</code>，至少比较 <code>OutImage0</code> 和 <code>OutImage1</code>，切换 <code>RefreshFlag=0/1</code>、<code>BufferCount=0/15/16</code>，并在缓存未满时连空槽；随后进入 owned Group、保存重开，再运行。逐步记录 <code>GraphExecutor</code> 的输入真实 Kind、队列长度/像素哈希、每个 <code>NodeRunRecord</code> 错误码。原厂侧需重新取得与安装 DLL SHA 一致的 <code>Process/CopyImage/Save/Load</code> 源/汇编或 SDK 重放；再判断“空槽缺席”和错误后旧缓存保留是否与本地外层执行语义一致。</p>
<h2 id="防偏差结论与交接">防偏差结论与交接</h2><ol>
<li><strong>当前能确认的范围</strong>：目录 19/143 映射和 18+Group 注册、缓存图像原 XML 端口结构、当前 <code>GraphExecutor → ImageBufferPlugin</code> 的载荷/状态/错误路径。图像源→二值化 RGB 断链已有独立实测，不用缓存图像的静态分析替代它。</li>
<li><strong>不能提前关闭的门</strong>：所有节点的 J04–J11 跨方案/Group 真实链，原厂图像格式与结果释放，二值化四个未执行模式，J12 卡死线程归因。既有 10/10 标定工具实施自审是另一明确范围，不等于这张矩阵 19 项已与原厂全域等价。</li>
<li><strong>下一轮最小实证包</strong>：先用同一 ImageSource→Buffer→Binary→实际下游图完成 J05/J06/J11 的成功和失败矩阵；Group、重开、撤销扩充 J09/J10；原始 Ghidra/SDK 证据补齐后才裁定插件侧改动。框架拥有连接/调度/作用域/持久化合同，插件线拥有工具端口、运行与配置；跨边界提 FCR，由用户决定采用。</li>
</ol>
<p>本轮是审核与证据纠偏，没有产品代码实施，也没有把任一 96 项框架单元计入新增完成。</p>
