<h2 id="当前适配与前轮实测边界">当前适配与前轮实测边界</h2><p>当前 <code>src/VisionPlugins.Calibration/ReadCalibFileConfiguration.cs</code> 的文件按钮经 <code>IToolConfigurationFileService.Select</code>；用户选中时 <code>State.CommitUser(..., forceWrite:true)</code>，配置 dispatcher 立即加载/解析，成功将 <code>FilePath</code> 与 <code>OutputSchema</code> 一次 <code>ApplyValues</code> 到图文档，随后 <code>RefreshData</code> 更新专属面板。失败路径有独立 host 事务拒绝/恢复策略。这是<strong>当前独立实现</strong>，不能把原 override 默认 <code>ReadData(false)</code> 说成它的原版依据。当前 GUI 侧失败/恢复的范围应参考插件 <code>ReadCalibFile</code> 专项，联合主框架动态结果则已有 <code>docs/joint-audit/20261020-pass12-readcalib-schema.md</code>：成功解析后改名/改型可更新运行 descriptor，但旧 Group 输出引用不自动迁移。该报告的当前真实图与本轮原控件按钮仍是不同入口，不能相互冒充原厂闭环。</p>
<h2 id="结论与精确缺证">结论与精确缺证</h2><p><strong>关闭一个歧义：</strong> <code>OpenFileDialog4ReadFile.ValueChangedCmdExecute → ReadFileConfigData.ReadData()</code> 的直接 UI 更新路径不调用 <code>VmModule.InitDynamicIO</code>，也没有 <code>ReadData(true)</code> 的默认参数。原文件控件选路径首先走基类写参/可选预运行，再读配置显示。此前若从 <code>ReadFileConfigData.ReadData(true)</code> 的实现推称“选 XML 自动删旧 Group 输出并重建”，该推称没有本入口的调用证据。</p>
<p><strong>仍需的唯一外层桥证：</strong> 文件选择写入 <code>FilePath</code> 后，原模块 SDK <code>SetParam</code>/<code>LoadFile</code> 或 <code>VmModule.Run</code> 是否发出动态 IO 通知，再由哪个托管 caller 调 <code>GetModuOutputIOInfo→InitDynamicIO</code>；还需确认对象复用/重建和已选 Group 关系是怎么处理的。现有原 <code>UpdateModuleStateOperation</code> 不能当作此 caller。原平台同构受控运行可作为反证/佐证，但没有该证据前对原版连接迁移一律记未知。无可依据的产品修复，不新增重复当前主窗探针。</p>
