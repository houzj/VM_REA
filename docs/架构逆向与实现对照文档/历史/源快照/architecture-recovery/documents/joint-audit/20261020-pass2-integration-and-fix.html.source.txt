<h2 id="已改变的判断">已改变的判断</h2><ul>
<li>原 <code>VmModule.PreModules</code> 不只是视图中的静态连线：首次访问由 <code>GetMultiModuleConnect</code> 从 SDK 获取同容器连接，后续 <code>NextModules.CollectionChanged</code> 增删同步目标前驱。原 <code>Group.xml</code> 的 <code>InputImage</code> 和 <code>InputMask</code> 都查询 <code>IMAGE</code> 组合；<code>GetFrontIOWithLeafItemsByName</code> 只按组合类型、可订阅、可见过滤，未按像素格式叶过滤。详情与完整 CIL SHA 见原 IMAGE 报告。FCR-031 已按该证据修订。<strong>候选可见不等于 RGB 可以被二值化执行。</strong> 原 Binary 原生输入格式分支仍缺。</li>
<li>当前目录快照是 143 项，19 项有映射，其中 18 个插件加内建 Group；124 项未映射。没有将它与历史 162 项混算。缓存图像原 XML 声明 15 个图像槽，当前 ImageSource→Buffer→Binary 真实图执行 8 态通过，日志 <code>analysis/joint-audit/mapped-tool-matrix/framework-image-buffer-chain.log</code> SHA-256 <code>3C91F51DFB127AE8A4EE4C60DAA3F2752CDB89A354F399322A4D727FCABCA2E9</code>。RGB 所在槽接 Gray 消费者会 <code>InputTypeMismatch</code>；空槽是 <code>UpstreamUnavailable</code>；数量 16 是 <code>InvalidBufferCount</code>，下游 <code>ExecutionPredecessorUnavailable</code>。旧原生缓存导出当前缺席，8 态只是<strong>本地实现</strong>检查。</li>
<li>无响应路径中，普通流程 <code>WorkflowExecution.RunCore → SolutionExecutor.RunAsync → GraphExecutor.RunAsync</code> 在首次未完成的 await 之前同步工作；二值化 <code>ExecuteAsync</code> 返回立即完成的 <code>ValueTask</code>，像素循环不会异步让出。受控图像源→二值化线程探针在调用线程完成，耗时 123.79 ms，JSON <code>analysis/joint-audit/hang-diagnostics/execution-thread-probe.json</code> SHA-256 <code>45A581C49D4F6856FA15C36743AB2114B157703BECBC5BF83C8CA8B79EC86F4C</code>。当前配置自运行已有 <code>Task.Run</code>，两条宿主路径不同。原 UI <code>VmProcedureDecorator.RunOnceCommandExe</code> 在 <code>analysis/decompiled/VMControls.WPF/VMControls.WPF.DataForUI/VmProcedureDecorator.cs:461-470</code> 调 <code>VmProcedure.Run(null,bIsWait:false)</code>，源文件 SHA-256 <code>A229FE33277EB857A0AFA3F6A9FDB56807D2178AD5E6958B28BC63175CE19B5A</code>；原 SDK 返回前的实际工作线程与回调仍未证实。用户那次空闲卡死没有 UI 线程栈，不能据此归因。</li>
</ul>
<h2 id="主框架最小修复与自审核">主框架最小修复与自审核</h2><p><code>src/VisionEditor/WorkflowExecution.cs</code> 现在在 UI 上先捕获 <code>Progress&lt;ExecutionEvent&gt;</code> 的 Dispatcher 上下文，再把 <code>SolutionExecutor.RunAsync</code> 交给 <code>Task.Run</code>。完成后的 owner 校验、状态/结果提交、关闭与取消仍在现有 await 后的 UI 路径。此改动针对<strong>已证实的当前同步阻塞机制</strong>，是本项目独立的宿主响应性修复；原版 <code>bIsWait:false</code> 是方向依据，不能宣称 native 调度逐指令相同，也不能宣称用户那次卡死已修好。</p>
<p>新增 <code>tests/WorkflowDispatcherChecks</code> 在自有受控 WPF 宿主中注册同步阻塞模块：模块未释放时 UI Dispatcher 可以处理脉冲，模块线程 5 与 UI 线程 2 不同，释放后流程与 owner 正常完成。日志 <code>analysis/joint-audit/20261020-workflow-dispatcher-check.log</code> SHA-256 <code>609E208A159715FBC52E64A7012E5B724B749D23B7E93A09CBB7BBF146390C87</code>；检查源 SHA-256 <code>BE8262E30A0820EB9930F4142DCA1F77CB2E23584AA503FCB119B18AA0132B55</code>。该探针不操作用户桌面、不涉及原生 SDK。</p>
<p>验证：<code>VisionEditor</code> Release 构建通过（最终增量日志 <code>analysis/joint-audit/20261020-editor-build.log</code> SHA-256 <code>88EDA00B7B4B4482BAA0BFEE9622482519A2C32827B2C0FFF6A49CB7C7FF2D8F</code>）；<code>ExecutionOwnerLifecycleChecks17</code> <strong>16/16</strong>，<code>CallbackQueueBeforeChecks22</code> 通过；图像源→二值化经 <code>GraphEditorDocument</code> 保存重开再执行 <strong>4/4</strong>，缓存链 <strong>8/8</strong>，UI Dispatcher 新检查 <strong>2/2</strong>。保存重开的 4 态日志 SHA-256 <code>27062F9DA81A9DD7F65A6548E087C48A34574573AB8BC063D49509BFA79AA99D</code>。这些是当前实现自审，不是原机桌面差分。</p>
<h2 id="剩余精确界限">剩余精确界限</h2><p>J04 的原厂候选集合和连线维护静态链已证；配置窗口保持打开时的刷新、变量/Group 跨层行为与 <code>.sol</code> 重开链未证。J05 的原版 Binary 对 RGB24、MONO8 和掩膜的格式门仍缺原生 <code>ProcessAlg</code>/算法库函数体与汇编；REA Ghidra provider 本轮 <code>not_configured</code>，历史导出路径缺席。J12 仍缺同构方案的 UI 心跳/分段时间线，以及停顿时的受控进程 UI 线程栈/等待链；首次路由约 149 ms/68 MB 是候选成本，不能解释持续空闲卡死。普通流程改为工作线程后，各具体工具若有 UI 线程亲和的隐藏副作用，仍需逐插件 J10 审核；本轮现有关闭/回调检查通过不消除该边界。</p>
