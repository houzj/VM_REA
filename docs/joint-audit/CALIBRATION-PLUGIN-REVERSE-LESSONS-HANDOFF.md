# 标定十工具联合审核：交给插件项目的方法修正

本文件是 main 对 `tool-plugins` 所有者的**候选交接**，不等于插件项目已采用。范围仅为十项标定工具的 UI、后台、算法及与框架必要的来源/Group/生命周期交接；其他类别另立目标。原源码、当前源码、运行探针和未知分别标识，不能用历史 `10/10` 实施自审代替联合 J01–J12 审核，也不能因本文件增加实施进度。

统一的[跨项目源码调用图](CALIBRATION-CROSS-PROJECT-SOURCE-GRAPH.md)是后续双方挂接专属 UI/算法的工作底图；它把可证边与待取回 caller 分开，不能以框图代替逐函数逆向。

## 已有源码条件下的逆向设计失效

当前偏差首先应归因于我们的逆向设计与退出判定，不应把“某段还没取到”当作原因或免责。已解出的工具函数、WPF 配置代码和框架代码本可按 caller/callee、绑定、参数、输出与消费者连成图；此前却按工具单体拆任务，并用单函数、单工具绿色探针关闭实施，缺少一个对十工具共享宿主和跨节点交接负总责的源代码调用图。`10/10` 是当时限定范围的实施自审，不能冒称已逐入口追通框架→工具→消费者。缺失的原始成员或 SDK 派发实现是**必须继续检索/反编译的工作项**，不是允许猜测或提前结项的理由。

以下实例分别区分“已有源码未沿链使用”“原始体尚待检索”和“当前探针揭示的实现差异”；不将它们混称源码不可得。

1. **已有代码没有按跨程序集调用图追完就收口。** 标定加载专用按钮 `OpenFileDialog4ReadFile.ValueChangedCmdExecute` 的基类写参、`ModuleParam→ModuleManager.SetParamValue→IMVS_SetParamValue`、原生 `CMyAlgorithmManager::SetParam(FilePath)→LoadFile` 与托管 `VmModule.Outputs` 均已有源码或反编译体，却直到联合审核才被并列成同一条待闭链。SDK 通知已加载 `Outputs` 与 Group 旧订阅的中间体仍须定点检索，不得以它缺席为由让该链通过。不能以“按钮里没有 InitDynamicIO”断言原厂不会刷新，也不能把原 `DynamicVmIO` 手动改名历史路径套用到文件路径 setter。证据：[第十三轮](20261020-pass13-readcalib-filepicker-dynamic-io.md)、[第十五轮](20261020-pass15-readcalib-dynamic-history-boundary.md)、[第十七轮](20261020-pass17-readcalib-native-callback.md)。
2. **把函数单测当成宿主调用链验收。** N 点点表原版 setter 逐叶写参数；当前主窗打开点表时 4/12/32 行分别产生 20/60/160 次文档 Revision/Changed，每次会触发宿主刷新。算法输出正确并不覆盖编辑成本。FCR-033 与[真实主窗探针](20261020-pass11-npoint-mainwindow-cost.md)记录了事实；这并未证明用户长期无响应的根因，仍缺当次 UI 线程栈。
3. **忽略结果属于哪一轮、哪个方案。** ReadCalib 当前非有限值失败时 loader/Group 已失败，`LastDisplay` 仍可能取上一轮 `Module Status:1`；畸变失败也可能留上一轮两层图。这些是当前缓存归属事实，原厂失败画面未证，不能统一清空或一律保留。见 FCR-034/036 与[标定加载状态链](20261020-pass16-readcalib-display-chain.md)。
4. **把 XML 声明误当算法谓词。** Rotate 原 `InputImage` 四叶 `IsForce=true`，当前聚合 `InputImage` 为可选；原 `Process` 未证读取图像。差异确定在端口/绑定合同，尚不能推出无图时原算法必定拒绝。见 FCR-035 与[旋转链](20261020-pass14-c-display-chain.md)。原生反编译显示参数数目时还须检查 RCX/RDX/R8/R9 活性和 ABI；标定板 EdgeThresh 的反例见 `docs/plugins/CALIBRATION-BOARD-EDGE-THRESHOLD-BRIDGE-TRACE.md`。
5. **将“节点不在图上”误当资源已释放。** 原 `VmModule.Dispose` 清关系、IO、父容器与 SDK 实体；当前由文档事件→执行域状态回收。第十七轮真实主窗标定板探针只证当前托管 state 删除/撤销/方案替换 6/6，不能推出原生资源或运行中取消等价。见[生命周期边](20261020-pass17-calibration-lifecycle.md)。
6. **以成功状态代替当前数据来源核对。** 标定加载文件从 `OldMatrix` 改为 `NewMatrix` 而文档保留旧订阅时，当前 warm 坐标系依靠上一轮矩阵仍能让 Group 成功，冷域则因矩阵未初始化失败。只看 `Success` 或相同九项矩阵会误判新叶已经接通。显式 schema+订阅重绑的 Undo/Redo/重开另可正常通过。当前行为、原版未证边见[第十七轮 Group 历史](20261020-pass17-readcalib-group-history.md)；是否禁止 warm 旧值是跨界政策，不能擅称原版要求。

## 下一次插件线应采用的有限门槛

每项工具必须先固定 `入口/资源→事件→参数或订阅→SDK/native→输出/错误→显示/Group→保存与历史→释放` 的**原版实际调用图**，列出每条边的原始类型/成员、caller/callee、读写字段、分支谓词、CIL/汇编或资源位置，再逐边映射当前实现和运行证据；一个成员缺失立即成为定点取回任务。只有确证原版代码本身不可还原时才列有限未知，并记录已尝试的文件、RVA/token 与失败原因。共同宿主边只取一次，但每项特有 UI/算法/错误分支不得被共享链代替。

设计和复核实行两道独立门：**先完成原始调用图，再评实现**；**先做跨节点与失败/历史/重开探针，再计工具自审完成**。算法保留同输入、参数、输出的原生夹具与反例，不能用同一正常矩阵让所有工具“通过”。动态端口、示教/批次和结果显示同时做暖态、冷态、失败恢复、撤销重做、保存重开，记载身份与运行轮次。每次发现偏差，应回查最初是哪条源码边未登记、哪一条测试没有覆盖，而不只对现象补丁。

交接时每个差异须给生产者、消费者、载荷、生命周期、旧方案兼容及最小接受证据，并指明唯一代码所有者。插件侧配置模型/专用编辑器/执行会话由 `tool-plugins` 所有；main 只负责图、Group、调度及跨界合同。本清单及 FCR 由用户选择何时交给插件工作树实施；不得直接修改其在制文件或自动合流。人工桌面验收及原厂设备差分与代码级自审分列。
