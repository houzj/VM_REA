# 第十七轮：标定加载 FilePath 到动态输出重建的源码边界

范围仅为原厂 `ReadCalibFileModu` 文件路径写入→SDK 参数 setter→原生文件解析/动态输出声明→托管 `VmModule.Outputs`。第十三轮已证明控件 override 自身不直接调用 `InitDynamicIO`；本轮向下追到原生 setter 和向上追到宿主输出懒加载，明确中间缺失的通知边。不修改产品、共享或 `tool-plugins`，没有在安装原件启动服务。

## 已证调用链

1. 原专用控件 `OpenFileDialog4ReadFile.ValueChangedCmdExecute` 先 `base.ValueChangedCmdExecute()`，再私有 `ReadData()`；后者无参调用 `ReadFileConfigData.ReadData()`，只刷新 `CalibInputParam` 的显示。反编译路径 `worktrees/tool-plugins/analysis/full-audit/calibration-dependencies/decompiled/ReadCalibFileModuControl/Apps.XmlParser.ParamTab/OpenFileDialog4ReadFile.cs`，哈希/REA CIL token 见[第十三轮](20261020-pass13-readcalib-filepicker-dynamic-io.md)。本 Control 反编译中 `ReadData(true)` 没有调用者；不能拿它的删旧 output 分支替代文件选择事件。
2. 原 `OpenFileDialog.SetCurValue` 依次写空值和选择路径；`ValueChangedCmdExecute` 在路径非空、连接可用时调用 `SetParamUnit()`。`NameValueItem.SetParamUnit→SetParamUnitByZmq→SetParamUnitDirect` 对 RW/Check/异常分支把 `ComName=FilePath` 写入 `AlgorithmTabRoot.UserStringData`。源 `analysis/decompiled/Apps.XmlParser.CapabilityAudit/Apps.XmlParser.ParamTab/OpenFileDialog.cs` SHA `129D9185E0FBDCCD5146EA57C1CA9033AB1D4D0AAF8EEFE29FCA2B1921C40BC4`，`NameValueItem.cs` SHA `90B4742E79243F46C46FD6B38187EE7F5BE49D4C6677F994133215A3796FED46`。基类写入成功才可选 `PreExecuteRun`；派生 override 的 `ReadData()` 不受其成功返回控制。
3. 原 `VM.Core.ModuleParam` 实现 `IUserStringData` 索引器：非全局模块在未 Dispose 时先 `RecordParamUnRedo(key)`，再 `SetValueBySDK(key,value)`，随后 `Parent.OnModuleParamChanged(key)`；`SetValueBySDK` 普通参数调用 `ServerSDKManager.mModuleManager.SetParamValue(Parent.ID,key,value,bThrowException:true)`。`VM.PlatformSDKCS.ModuleManager.SetParamValue` 调 `ServerSDKAPI.IMVS_SetParamValue(handle,moduleId,paramName,paramValue)`，错误时抛 `VmException`，成功则 `ParamSeted=true`。P/Invoke `NativeMethods.IMVS_SetParamValue` 使用 UTF-8 marshaler。源分别为 `analysis/decompiled/VM.Core/VM.Core/ModuleParam.cs` SHA `AF392BF2D3AF006C6A16021A271D67DD8EF2017B268580841874AB6FEDE1DA48`、`analysis/decompiled/VM.PlatformSDKCS.Audit/VM.PlatformSDKCS/ModuleManager.cs` SHA `783A45B1518F713223ECA2B5E59291BE973552C3E08FEF0EA0D4BFCCC2FBD922`、`NativeMethods.cs` SHA `6A60F612FB385987FF96D6973844A256402F097D1EB371E7AD462C44E57127D0`。这证明托管调用到 P/Invoke 边；`IMVS_SetParamValue` 平台服务内部派发函数体未在该源码中。
4. 原 `ReadCalibFileModu.dll` 的 `CMyAlgorithmManager::SetParam` RVA `0xd120`，`worktrees/tool-plugins/analysis/full-audit/read-calib-file/native/18000d120.c` SHA `35DC0C1699E08DFCE863173B529FBE8BA4E0579BE5D6CE1D3167AEE92D2F57F5`：`FilePath` 非空走 `LoadFile` RVA `0xab50`，空值清路径/结果向量；`DynamicOutData` 分支则复制二进制数据并调用 `FUN_180009410`。`LoadFile` 反编译 `.../18000ab50.c` SHA `EC0CFDED878E3B054A65F8F83550364D74503B59D792069D0566C42D91231626`：解析输出名/类型，打开失败保留旧集合，成功解析后替换集合；详见已有第七轮失败链。此两条参数名在同一 setter 中是**不同分支**，不能从 FilePath 自动推定调用 `DynamicOutData`。
5. 原 module 初始声明 `Output/DynamicOutData` 见 `.../180009a90.c` SHA `F3B1A8807F67EE59E880DF7FEBD80E4121E96F5094C2A8A2760DCBF6A1A55B8D`。`SaveModuleData` helper RVA `0xcf10` 将当前 `DynamicInData/DynamicOutData` 指针、长度打包到持久化数据，`.../18000cf10.c` SHA `3DA32B425392DB3191E036502F8DAC4328FA0F9002528106F135B08E9708DDAD`；载入路径 `.../18000bef0.c` SHA `EEAC7FA3C98184213039400B00DD423B1708C082B348EF4B384D7C9BC48D9BEB` 再经 vtable `SetParam` 恢复。此边证明二进制动态 IO 配置可保存/恢复，**不是**文件路径写入即时触发同一分支的证据。
6. 原 `VM.Core.VmModule.Outputs` 首次访问在 `!outputs_IsLoaded&&!VmSolution.IsLoading` 时调用 `InitOutputDynamicIO()`；后者从 `ModuleManager.GetModuOutputIOInfo(ID)` 得到 SDK IO 信息后 `InitDynamicIO(list,_Outputs)`。`InitDynamicIO(list,collection)` 遍历信息并 `AnalysisIOInfo`。`InitDynamicIO()` 无参另读取双向 IO。源 `analysis/decompiled/VM.Core/VM.Core/VmModule.cs` SHA `53E2F0F9032C4631B59CF0EB2A00E06D50469D94706E7E370E9CC7E1059C72CE`。这证明**有一条** SDK schema→托管输出列表构建路径；首次 Outputs 已载入后，单靠该 getter 不会再调用初始化。`ModuleParam.OnModuleParamChanged` 在该反编译源码里仅派发 `ModuleParamChanged` 事件，没有直接 `InitDynamicIO`，外部订阅者尚未完整取证。

## REA/CIL 与缺失桥

REA `inspect_managed_members` 对原 `D:/Program Files/VisionMaster4.4.0/Applications/myLibs/VM.Core.dll`（SHA `936763F6C8A1BF9FCF59F22ACEBCA8FEB09B5F3D5701AE77C82BDC81E626190D`）返回 `ev_a0fe9942b44512a7e9e64349ba6fbc3a7cf996530186b77707d9bf023005cc9d`，coverage=`unavailable`：metadata representation 超过 64 MiB 预算；不能把上述反编译源码伪称此次 CIL 重验。原 `D:/Program Files/VisionMaster4.4.0/Applications/PublicFile/x64/VM.PlatformSDKCS.dll`（SHA `34C0C90B00CB75A701685B96670B6490F61376F62EACC0AB29D240157DB401C1`）同样返回 `ev_de13b657e3113b360efba931e280afdfd22fb5cd1901b38dcf2f58204aa718b7`、同一预算限制。第十三轮专用小 Control.dll 的 CIL 则已成功取得，未重复调用。

当前能精确画出的链为：`FilePath UI → IUserStringData[FilePath] → ModuleParam.SetValueBySDK → ModuleManager.SetParamValue → IMVS_SetParamValue(P/Invoke)`；模块入口 `CMyAlgorithmManager::SetParam(FilePath) → LoadFile` 是另一端经原生模块算法管理器确认的边；宿主 `GetModuOutputIOInfo → VmModule.InitOutputDynamicIO/InitDynamicIO` 是消费端。**尚缺**平台服务 `IMVS_SetParamValue` 如何派发到模块 setter、是否在文件成功/失败后发 IO schema 通知、哪个已存在的 `Outputs` 实例收到通知并在何时重建、既有 Group 绑定是按身份保留还是按名重匹配的源码/CIL/运行证据。原 UI override 既不直接 `InitDynamicIO`，原 `ModuleParamChanged` 本体也不直接做它；这不是“原版不会动态刷新”的证明。

下一最小取证点：对原平台 `IMVS_SetParamValue` 的 service/模块管理代码或受控回调 trace 定位 setter 派发与 IO 信息通知；同时捕获 `VmModule.ModuleParamChanged` 的**实际订阅者**及文件选择后 `outputs_IsLoaded` 状态。没有这条证据，不修改当前输出 schema 迁移策略，也不把 `DynamicOutData` 持久化分支当即时 callback。
