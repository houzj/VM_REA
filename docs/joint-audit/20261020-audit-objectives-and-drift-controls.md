# 框架到节点联合审核目标与防偏差闸门

日期：2026-10-20。审查基线为 main `120611182c8908334298ba47eb9244bb1f9b6307` 加已明列的未提交工作区；不得将工作区状态称为已交付基线。本文是**审核规则和任务清单**，不改变既有 `framework-reverse-plan.json` 的 96 个框架实施单元，也不改变用户对人工验收后置的要求。

## 1. 审核目标和固定范围

目标不是检查单个窗口是否像原版，而是对每个已接入工具建立一条可追溯的链：

`原厂模块/资源身份 → 工具发现与实例化 → 配置模板及事件 → 输入候选/连接/订阅 → 真实数据形状 → SelfRun/全流程/Group → 输出与显示 → 失败/取消/释放 → 保存/重开/撤销`。

每条边同时核 **原版证据、当前实现、可复验操作**，缺一项就保留开放状态。原厂证据必须到类型/成员/资源/分支；原生反编译歧义要核调用前后指令、ABI 与异常路径。截图只指出待审状态。当前源码恰好能运行、测试通过、某个数值夹具相同，都不能把未知原厂行为改写成“已复刻”。

范围分层，不能混算：

| 层 | 本次审核范围 | 计数口径 |
|---|---|---|
| 已接入联合链 | 当前 `tool-catalog.json` 工作区快照中 19 个有 `ModuleId` 的条目（含 Group）；逐项核真实注册、配置、端口和宿主使用 | 这是**审核对象数**，不是完成数；其中 Group 是框架伪模块，不按普通插件算法计算 |
| 未接入目录 | 当前目录另有 124 个 `ModuleId` 为空的条目 | 只做身份/依赖/证据入口清点；不把目录存在当插件已实现或可运行 |
| 历史全目录 | 旧插件清单记录的 162 项 | 是不同快照/清点口径，须先按原厂身份去重、版本对齐，不能与当前 143 项目录直接相减 |
| 框架实施进度 | 既定 96 个具名单元 | 当前权威值仍为 41/96=42.71%；本审核只读或探针不增加实施分子 |

## 2. 单工具必须通过的 12 个审核目标

每个目标记录 `原厂路径+SHA/精确成员或地址`、`当前生产代码路径`、`实测输入/命令/输出`、`失败与未知`、`责任方`。以下是审查门，不是新增的 12 项进度分母。

| ID | 目标与必查问题 | 关闭所需证据 |
|---|---|---|
| J01 身份/依赖 | 安装包版本、模块 ID、托管/原生 DLL、资源、SDK、依赖是否匹配实际启动版本？ | SHA/MVID、入口符号、注册映射、受控构建 EXE 身份一致；旧导出缺席必须标明 |
| J02 发现/创建 | 原厂如何加载、分类、启用和生成节点？当前目录、注册表、拖放是否同一工具？ | 原工具箱/装载调用链；当前 catalog→registry→node 实际路径；缺插件/冲突/失败不留悬挂节点 |
| J03 配置 UI/事件 | 默认、范围、显隐、模板键、编辑提交/取消/关闭、复位写到哪一层？ | XML/XAML→绑定/命令→setter/参数对象→运行读取；测试打开、单字段编辑、复位、失败回滚 |
| J04 来源候选/连接 | 未连接、建立连接、切换输出、断开、Group/变量边界时候选和已选值如何变化？ | 原 `Group.xml` 操作体及其消费者/通知；当前候选、`Connections`、`Subscriptions` 三态分别核对，标签不当身份 |
| J05 类型/载荷 | 声明端口与实际图像格式、数组、ROI、Fixture、动态叶、可选输出是否一致？ | 原参数/IO 校验与像素/结构 ABI；当前 producer→validator→executor→consumer 的真实载荷与错误码；含负例 |
| J06 运行/调度 | SelfRun 是否准备上游？整流程、连续、超时、Stop、Group 是否共享输入和状态？ | 原 Run→SDK/模块→回调与状态链；当前缓存来源和执行拓扑；至少未运行/已运行/上游已变三状态 |
| J07 算法/结果 | 参数读入、数值精度、ROI/Mask 顺序、输出、NoMatch/失败结果是什么？ | 原生函数体/指令或可复验原机/SDK差分；多夹具正负例；不能用一个像素样本推公式 |
| J08 显示/预览 | 输入预览、结果图、覆盖层、指标及运行时间是否来自同一结果对象？ | 原输出/显示资源与绑定；当前运行结果→显示 adapter→窗口；失败和切换节点后不残留旧结果 |
| J09 持久化/历史 | 参数、连接、资源路径、ROI、动态 schema、Group 身份保存/重开和撤销后是否相同？ | 原格式/调用链与当前格式**分别**验证；重新实例化宿主后执行，不能只验证 JSON 反序列化 |
| J10 生命周期/并发 | 创建、重开窗、切方案、重复运行、取消、失败、关闭时资源谁拥有、谁释放？ | 原 ctor/Dispose/DeInit、事件订阅/异常区；当前 owner epoch、scope、缓存与资源计数；旧回调不可写新方案 |
| J11 跨节点闭环 | 工具输出能否被真实下游消费，在 owned Group 中是否维持同样语义？ | 同一方案至少一条有实际 producer、待审工具和实际 consumer 的完整链；普通流程与 Group、重开后复跑 |
| J12 宿主性能/卡死 | 空闲、配置编辑、运行/显示期间 UI 是否失去响应？耗时落在哪一段？ | 同构方案的 UI 心跳、分段耗时、线程 ID；重现时受控实例 UI 线程堆栈/等待链；无栈仅记候选 |

状态只使用 `confirmed-original`、`confirmed-current`、`differential-confirmed`、`independent-compatibility`、`blocked-exact-evidence`、`not-started`。一项可同时有原版确认和当前差异，但不能用“部分通过”掩盖缺失调用边。所有 `blocked` 必须写明**准确缺哪个函数/资源/运行条件及解除方法**，不能反复以“继续逆向”派同一题。

## 3. 对现状的完整风险判断

| 优先级 | 事实、风险或边界 | 下一条能改变判断的证据 |
|---|---|---|
| P0：无响应 | 用户观察是**先卡住，再因下一次操作出现未响应弹窗**。2026-10-20 Application Hang 1002 证实当前重建版一次失去交互；没有线程堆栈。当前 `doc.Changed→RefreshAll→GraphValidator/RenderGraph/RefreshRight` 为同步 UI 路径，配置提交与结果回调会触发刷新；路由重算仅在相应端点/端口缓存失效等条件进入。它们都是候选，不是根因。 | 自有受控实例的 UI 线程堆栈、等待链和分段计时；把空闲、后台刷新、运行和编辑四类场景分开。无栈时不得针对猜测热点宣称修好卡死。 |
| P0：二值化模式 | 原 XML 显示五模式，当前窗口可选五模式，运行时仅硬阈值，其余返回 `BinaryModeUnavailable`。原托管 Run 到 SyncSelfRun 可证，原生算法与失败释放链缺本轮可复验函数体。 | 重新取得与原 DLL SHA 对应的 `Init/SetParam/ProcessAlg/ProcessOutput/DeInit`、SDK Run 和 core 算法指令；多夹具差分。未取齐前保持独立实现/未支持标签。 |

## 4. 每轮审核的固定工作包与退出门槛

**第 1 包：排除误判。** 固定当前 EXE/方案/样图身份，建立受控无响应诊断，取得 UI 线程停顿点；并复验二值化 RGB/Gray 图执行与直接运行两种错误路径。退出物：事件/堆栈/计时（若未重现，明确未重现条件），以及已保存的输入类型探针。当前只有事件和类型探针，卡死原因**未关闭**。

**第 2 包：原版共同合同。** 获取候选/连接/像素格式、SelfRun 上游准备、输出清理的原方法体或受控差分；以 ImageSource→Binary→实际下游为首条链，同时用 N 点复杂配置/Group 与一个非图像节点检验规则通用性。退出物：J04–J10 的逐边矩阵，不得以 XML 声明替代运行边。

**第 3 包：按工具簇推广。** 已接入的图像源/二值化、十个标定、位置修正、分支、多图/缓存/光源按实际依赖分组；每个工具先做 J01–J05 静态与类型检查，再做 J06–J11 完整链。设备不可用时明确隔离设备分支，不能把无设备模拟当原机证明。未接入目录只做证据/依赖清点，待用户指定实施范围。

**第 4 包：闭环和防回归。** 对已确认差异按所有权实施最小改动，保留失败样本；同一实际方案做根流程/Group、Undo/Redo、保存重开、失败/取消/关闭；主线串行构建与检查。每个改动须指出所修 J-ID 和原始分支。自审核通过的框架具名单元才增加 96 分母的实施进度；联合审核本身不抬进度。

每包开始先固定 1–3 个**能改变状态的具体问题**及退出证据；结束公布已关闭/未关闭 J-ID、真正新增的实施单元、当前 41/96 基数、阻塞解除条件。若原生 provider 不可用，继续托管 CIL/资源/调用者/受控探针等独立可做部分，但不得用新增报告数量替代问题关闭。

## 5. 防止“越逆越偏”的强制复核

1. **反向可证伪。** 每个推断都列一个会推翻它的输入/状态。比如“原厂自动灰度化”必须能被 RGB 输出、输入格式字段、原生校验分支和输出像素验证；缺其一只写假设。
2. **保留负例和旧失败。** 新测试通过不覆盖旧失败；身份变更、依赖变更、代码重构后按受影响调用边重跑，不复制旧日志充当前基线。
3. **原版与兼容层分栏。** 原厂 `InputImage`、本地 `Image`、原厂 `.sol`、本地 JSON、SDK SelfRun、本地缓存自运行分别列名，禁止同名化后宣称等价。
4. **证据修订机制。** 当新 CIL/汇编/原机差分推翻旧结论，记录旧主张、反证、受影响实现/测试/文档，撤销相关完成状态；原生 ABI 尤其不能凭反编译器展示的实参数量断言丢参。
5. **所有权约束。** 主线审框架合同、调度、Group、存储和集成；插件线审工具算法与公共插件配置。跨线字段/端口/生命周期修改先登记 producer、consumer、payload、生命周期、兼容和接受证据，指定唯一写入者；`tool-plugins` 在制文件保持不动。
6. **操作证据不混层。** 源码确认、当前产品自测、SDK 探针、原厂桌面差分、人工验收分别标记。离屏窗口不能算用户桌面手验；安全拒绝未知 native 行为不是算法复刻。

最终可交付的“完整审核”应是一张每工具×J01–J12 矩阵、原始证据索引、差异/FCR、可复验探针与失败库、实施提交和剩余未知清单。只有所选范围内所有目标的证据门满足、差异已实施并自审，才能宣称该范围闭合；人工验收继续单列，不计实施百分比。
