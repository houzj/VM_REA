# Parallel reconstruction work

Read docs/PARALLEL-WORK.md before making changes. Use decompiled source, resources and confirmed runtime evidence as implementation evidence; user feedback identifies differences and is not a substitute specification. Distinguish source-confirmed behavior, independent implementation, and unverified native behavior. Never claim complete parity from passing tests alone.

## Source-level reconstruction standard (standing user requirement)

Reconstruct behavior from the original program's decompiled source, shipped resources and confirmed runtime evidence at the call-chain/data-flow level. Trace the relevant entry point through bindings, commands/events, state changes, persistence and execution effects before implementing. Do not substitute inferred product intent, screenshots, conventional UI patterns, or a plausible design for missing evidence. Screenshots and user feedback identify a discrepancy or state to investigate; they do not define the implementation contract. When source evidence is incomplete, record the exact unresolved behavior and label any independent approximation as such; do not present it as VM behavior. For each feature, retain source paths and exact types/members/resources, evidence type, confirmed behavior, reconstructed behavior, unknowns, and operation-level verification. Apply this standard to all future reverse-engineering work in this repository.
## Source-level reverse engineering standard

Use docs/SOURCE-LEVEL-REVERSE-PLAN.md to drive grouped reverse engineering. Obtain missing original member/function bodies and resources through REA before reconstruction. Recover concrete call paths, field reads/writes, branch predicates and lifecycle; native pseudocode requires assembly/ABI checks where ambiguous. A missing source body is a retrieval task, not permission to implement plausible intent. Keep source recovery, runtime corroboration, implementation and host acceptance as separate completion states.
